Implement a complete, centralized user profile-photo system in the CanYoldaşı application.

CURRENT STATE

On the “Hesap” screen, the top-left profile area currently displays a generic user icon inside a purple circular avatar.

REQUIRED RESULT

1. The user can tap the avatar to add or change a profile photo.
2. The photo is uploaded permanently to Supabase Storage.
3. The stored profile record is updated.
4. The same photo automatically appears everywhere that user’s avatar is shown.
5. Refreshing, restarting, logging out/in, or using another device must not remove the photo.

Do not implement this using local component state only.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
1. ACCOUNT-SCREEN INTERACTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Make the circular avatar in the top-left area of the “Hesap” screen pressable.

Add a small edit/camera badge at the bottom-right edge of the avatar so users understand it can be changed.

When tapped, open a Turkish action sheet:

Title:
“Profil Fotoğrafı”

Actions:

- “Fotoğraf Çek”
- “Galeriden Seç”
- “Mevcut Fotoğrafı Kaldır” — show only if a photo exists
- “İptal”

Expected behavior:

- “Fotoğraf Çek” opens the camera.
- “Galeriden Seç” opens the image library.
- “Mevcut Fotoğrafı Kaldır” asks for confirmation.
- “İptal” closes the sheet without changing anything.

If running in a simulator without a camera, handle the error gracefully. Do not show an uncaught Promise or red error screen.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
2. PHOTO SELECTION AND EDITING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

After selecting or taking a photo:

1. Allow square cropping.
2. Center the face where possible.
3. Use a 1:1 aspect ratio.
4. Compress and resize the image before upload.
5. Preserve sufficient quality for avatars.
6. Show a circular preview.
7. Ask the user to confirm with:
   “Profil Fotoğrafını Kaydet”

Recommended processed size:

- 800×800 or 1000×1000
- JPEG/WebP where supported
- Reasonable compression without visible quality loss

Correct image orientation using metadata when necessary.

Reject unsupported or excessively large files with a clear Turkish message.

3. CAMERA AND GALLERY PERMISSIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Request permissions only when the related action is selected.

Turkish camera permission explanation:

“Profil fotoğrafı çekebilmeniz için kamera erişimi gereklidir.”

Turkish gallery permission explanation:

“Profil fotoğrafı seçebilmeniz için fotoğraf arşivinize erişim gereklidir.”

If permission is denied, show:

“İzin verilmedi. Profil fotoğrafı eklemek için uygulama ayarlarından gerekli izni açabilirsiniz.”

Include an “Ayarları Aç” action when permission is permanently blocked.

Handle Web, Android, and iOS separately without breaking another platform.

4. SUPABASE STORAGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Inspect the existing Supabase schema and Storage buckets before creating anything new.

Reuse the existing avatar/profile-photo bucket if one already exists.

Otherwise create or document a bucket equivalent to:

`avatars`

Recommended path structure:

`{authenticated_user_id}/avatar-{unique_version}.jpg`

Requirements:

- Only authenticated users can upload their own avatar.
- Users cannot upload into another user’s folder.
- Users cannot modify another user’s avatar.
- Profile photos must be readable wherever public user avatars are intended to appear.
- Add appropriate Storage policies.
- Validate file type and file size.
- Use unique filenames or controlled versioning to avoid stale browser and CDN cache.
- Do not store temporary `file://`, `content://`, or `blob:` URLs in the database.
- Store a permanent Storage path or valid permanent URL.
- Never expose a Supabase service-role key to the client.

Do not delete the current avatar before the new upload and database update succeed.

After a successful replacement, safely remove the old owned avatar when appropriate. Never delete another user’s file.

5. PROFILE DATABASE FIELD
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Inspect the existing profile table before adding duplicate fields.

Use the project’s existing profile-photo field if present, such as:

- `avatar_url`
- `avatar_path`
- `photo_url`
- `profile_photo`

Choose one authoritative field.

The profile record must belong to the authenticated user.

After upload:

1. Update the authoritative profile-photo field.
2. Verify the update succeeded.
3. Re-read the profile record.
4. Update the centralized user-profile state/cache.
5. Refresh all avatar components.

Do not use the authentication metadata and profile table as two conflicting sources of truth unless they are intentionally synchronized.

6. CREATE ONE SHARED AVATAR COMPONENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Create or update one reusable component equivalent to:

`UserAvatar`

It should accept parameters such as:

- `userId`
- `avatarUrl` or `avatarPath`
- `displayName`
- `size`
- `editable`
- `onPress`

Use this shared component everywhere rather than duplicating avatar URL logic.

Required behavior:

1. Display the user’s real profile photo when available.
2. Display initials when the photo is missing and a name exists.
3. Display the current generic user icon only as the final fallback.
4. Show a loading state without flickering.
5. Fall back safely if image loading fails.
6. Render as a circular image.
7. Use `resizeMode="cover"`.
8. Never stretch the photo.
9. Support multiple sizes.
10. Include an accessibility label.

Example fallback for “Tolga”:

“T”
