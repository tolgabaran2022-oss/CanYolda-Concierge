==================================================
IMPORTANT CONVERSATION RULE
==================================================

Adoption conversations must be linked to the adoption listing.

A conversation must know:

- conversation ID
- adoption listing ID
- pet ID if the project uses a separate pet record
- listing owner ID
- interested user ID
- created_at
- updated_at
- last_message_at

Example:

conversation:
id = conversation_123
listing_id = listing_123
owner_id = user_b
interested_user_id = user_a

The listing relationship is REQUIRED.

Do not create a conversation based only on two user IDs.

Reason:

The same two users may communicate about multiple different animals.

Example:

User A and User B can have:

Conversation 1:
Pamuk

Conversation 2:
Boncuk

These must remain separate adoption conversations.

==================================================

Connect the existing:

button.

Create one centralized function similar to:

handleMessageListingOwner()

Expected logic:

1. Verify authenticated user exists.
2. Get current listing ID.
3. Get listing owner ID.
4. Prevent the listing owner from messaging themselves.
5. Search for an existing conversation for:
   current user
   listing owner

==================================================

The user must only be able to access conversations they participate in.

Order conversations by:

last_message_at DESC

The newest active conversation must appear first.

==================================================
RLS AND SECURITY
==================================================

Audit and fix Supabase Row Level Security.

Conversation rules:

A user can SELECT a conversation only if they are a participant.

A user can SELECT messages only from conversations they participate in.

A user can INSERT a message only if:

auth.uid() is a participant of the conversation

AND:

sender_id = auth.uid()

The client must never be able to send a message as another user.

A user must not be able to change:

sender_id
conversation ownership
another participant's identity

through client manipulation.

Do not solve authorization with UI-only checks.

==================================================
DUPLICATE CONVERSATION PREVENTION
==================================================

Prevent duplicate conversations at database level where possible.

For an adoption listing, there should only be one active conversation for the same:

listing ID
listing owner
interested user

Use a database unique constraint or secure database function/RPC where appropriate.

Do not rely only on:

"check then insert"

from the client because rapid taps or race conditions may create duplicates.
