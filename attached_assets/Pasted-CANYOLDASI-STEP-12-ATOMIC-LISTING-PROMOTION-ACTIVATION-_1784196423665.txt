==================================================
CORE REQUIREMENT
==================================================

A promotion may only be activated by the backend after all of these are true:

1. Request is authenticated
2. Listing exists
3. Listing belongs to authenticated user
4. Package identifier is allowed
5. RevenueCat purchase is verified
6. Transaction has not already been processed
7. Purchase record is eligible for activation

The mobile client must never directly update:

promoted_until
is_promoted
promotion_expires_at
purchase_status = processed

2. SERVER-SIDE PACKAGE MAPPING
==================================================

Create one server-side source of truth:

boost_1_day -> 1 day
boost_3_days -> 3 days
boost_7_days -> 7 days

Do not trust:

durationDays

from the client request.

The client may identify the selected package, but the backend must derive the duration.

Reject unknown package identifiers.

==================================================
3. ATOMIC DATABASE TRANSACTION
==================================================

Use a real PostgreSQL transaction through Drizzle.

Inside one atomic transaction:

1. Lock or safely read the promotion purchase record
2. Confirm purchase_status is verified and not already processed
3. Confirm the transaction belongs to the authenticated user
4. Confirm the listing matches the verified purchase context
5. Read the current listing promoted_until
6. Calculate the new expiration
7. Update the listing promoted_until
8. Update the purchase record to processed
9. Store promotion_started_at and promotion_expires_at
10. Commit

If any step fails:

rollback everything.

Never allow:

listing updated
but purchase still verified

or:

purchase marked processed
but listing not promoted

==================================================
4. PROMOTION STACKING LOGIC
==================================================

Use this exact business rule:

If the listing is not actively promoted:

baseTime = now()

If promoted_until exists and promoted_until > now():

baseTime = promoted_until

Then:

newPromotedUntil = baseTime + durationDays

Examples:

No active promotion
+ 3-day package
= now + 3 days

Current promotion expires July 20
User purchases 3 days
= July 23

Expired promotion:
promoted_until is in the past
+ 1 day
= now + 1 day

Do not replace remaining active promotion time.

==================================================
5. TIME HANDLING
==================================================

Use database/server UTC time.

Do not use the mobile device clock as source of truth.

Do not accept timestamps from the client.

Use timestamptz-compatible values.

Avoid timezone bugs.

The API may return ISO 8601 timestamps to the client.

==================================================
6. IDEMPOTENCY
==================================================

The same verified purchase must never add time twice.

If the purchase record is already:

processed

return an idempotent response.

Example:

{
  "success": true,
  "alreadyProcessed": true,
  "promotedUntil": "..."
}

Do not extend the promotion again.

Use database uniqueness and transaction-safe status handling.

Protect against two simultaneous activation requests.

==================================================
7. ENDPOINT DESIGN

Reuse the existing secure verification endpoint if the architecture is clean.

Preferred final flow:

POST /api/promotions/verify-purchase

The endpoint:

- authenticates user
- validates ownership
- verifies purchase
- performs atomic promotion activation
- returns final promoted_until

Do not create several overlapping endpoints unless the current architecture intentionally separates verification and activation.

If verification and activation remain separate:

the activation endpoint must never trust a client-provided “verified” flag.

It must load the verified purchase record from the database.
