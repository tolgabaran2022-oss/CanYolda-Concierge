Bir kritik kod riski daha var: Worker’ın “SELECT ardından UPDATE” yapması, production’da birden fazla instance çalışırsa aynı eventi iki worker’ın seçip iki bildirim göndermesine yol açabilir. event_key UNIQUE yalnızca iki event kaydını engeller; aynı eventin iki worker tarafından gönderilmesini engellemez.

Önce Replit’e şu son düzeltmeyi gönder:

PRODUCTION PUSH WORKER — ATOMİK EVENT CLAIM VE DEPLOYMENT DÜZELTMESİ

Mevcut notification worker şu mantığı kullanıyor:

SELECT pending events
→ UPDATE processing
→ gönder

Bu yapı birden fazla backend instance/worker aynı anda çalışırsa race condition oluşturabilir:

Worker A aynı pending eventi SELECT eder
Worker B aynı pending eventi SELECT eder
İkisi de processing yapar
İkisi de aynı push bildirimini gönderebilir

`event_key UNIQUE` bu problemi çözmez; yalnızca duplicate event INSERT işlemini engeller.

1. ATOMİK CLAIM

Event seçme ve processing durumuna geçirme işlemini tek transaction içinde atomik yap.

PostgreSQL için güvenli yöntem kullan:

```sql
WITH claimed AS (
  SELECT id
  FROM notification_events
  WHERE status = 'pending'
    AND next_attempt_at <= NOW()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 10
)
UPDATE notification_events AS events
SET
  status = 'processing',
  processing_started_at = NOW(),
  attempts = events.attempts + 1
FROM claimed
WHERE events.id = claimed.id
RETURNING events.*;

Gerçek kolon adlarını mevcut şemaya göre düzenle.

Drizzle transaction/raw SQL yapısını mevcut projeye uygun kullan.

Şunları doğrula:

İki worker aynı eventi claim edemiyor.
Claim edilen event yalnız bir kez dönüyor.
attempts atomik artıyor.
next_attempt_at null ise uygun biçimde işleniyor.
Failed/retry eventleri yeniden claim edilebiliyor.
Maksimum attempt aşılmış event tekrar alınmıyor.
Stuck processing recovery aynı anda çalışan workerlarla güvenli.
Worker crash sonrası event yeniden işlenebiliyor.
TESLİMAT İDEMPOTENCY

Expo Push API tam olarak once-delivery garantisi sağlamadığı için:

sent event yeniden gönderilmemeli.
Worker restart sırasında sent event alınmamalı.
Receipt kontrolü push’u tekrar göndermemeli.
Ticket ID event kaydına yazılmalı.
Aynı event processing durumunda normal worker tarafından tekrar alınmamalı.
Stuck timeout, normal push isteği süresinden daha uzun ve makul olmalı.

60 saniyelik stuck timeout’un Expo API timeout/retry süresine göre güvenli olduğunu doğrula. Gerekirse artır.
