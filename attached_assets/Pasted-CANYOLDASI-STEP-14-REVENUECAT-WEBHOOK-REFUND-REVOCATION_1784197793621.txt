4. HMAC SIGNATURE VERIFICATION
==================================================

Also support RevenueCat HMAC webhook signing.

Use server-only environment variable:

REVENUECAT_WEBHOOK_SIGNING_SECRET

RevenueCat sends:

X-RevenueCat-Webhook-Signature

with a structure similar to:

t=<unix_timestamp>,v1=<hmac_sha256_hex>

Verification requirements:

1. Read the raw HTTP request body bytes exactly as received
2. Extract t and v1
3. Build:

<timestamp>.<raw_json_body>

4. Compute HMAC-SHA256 using REVENUECAT_WEBHOOK_SIGNING_SECRET
5. Compare using crypto.timingSafeEqual
6. Reject signatures older than 5 minutes
7. Reject malformed headers
8. Reject invalid signatures with 401

Do not:

- JSON.parse and JSON.stringify before signature verification
- compute HMAC from a reconstructed JSON object
- expose the signing secret
- skip verification in production

RevenueCat HMAC verification depends on the exact raw body bytes.

==================================================
12. PROMOTION REVERSAL BUSINESS RULE
==================================================

Implement this conservative CanYoldasi refund rule:

If the refunded purchase is the only active promotion contribution and can be reversed unambiguously:

reduce or end the promotion safely.

However, promotions can be stacked.

Example:

1-day purchase
then 7-day purchase

If the 1-day purchase is refunded, do not blindly set promoted_until = now() because the 7-day valid purchase must remain.

Do not subtract durations from a single timestamp without a reliable ledger.

Audit whether the database records every purchase contribution with:

promotion_started_at
promotion_expires_at
duration_days
purchase_status

Create a safe recalculation service.

Recommended approach:

Recalculate the listing’s valid promotion window from all non-refunded, non-revoked processed promotion purchase records.

Do not mutate time by simply subtracting duration from the current promoted_until.

==================================================
13. PROMOTION LEDGER RECALCULATION
==================================================

Create one centralized backend function such as:

recalculateListingPromotion(listingId)

It must:

1. Load valid processed promotion purchases for the listing
2. Exclude:
   - refunded
   - revoked
   - failed
3. Order purchases deterministically
4. Reconstruct the promotion timeline using server-side timestamps
5. Calculate the correct current promoted_until
6. Update adoption_listings.promoted_until atomically
7. Return the new promoted_until

Do not trust client dates.

Do not use the mobile clock.

Be careful with purchases made after an earlier promotion expired.

Do not incorrectly merge completely separate historic promotion periods.

Use the stored activation timestamps and durations to reproduce the actual promotion contributions safely.

If exact reconstruction is impossible with the current schema:

create the minimal safe migration needed to store contribution boundaries.

Explain the migration.
