İki önemli teknik risk kaldı:

Backend’de .catch(() => {}) ile yapılan tamamen beklenmeyen fire-and-forget çağrılar güvenilir değil. Serverless/request ortamı yanıt sonrası işlemi sonlandırabilir; bildirim hiç gönderilmeyebilir. Hata da tamamen kayboluyor.
Aşı, randevu ve ilaç hatırlatıcıları uygulama kapalıyken çalışmıyor. Kullanıcıya bu özellik sunulduğu için scheduler kurulmadan P0 kapanmaz.

1. FIRE-AND-FORGET GÜVENİLİRLİĞİ

Şu yapı güvenilir değildir:

```ts
sendPushNotification(...).catch(() => {});

Sorunlar:

Promise beklenmiyor.
Request/serverless işlem tamamlanmadan sonlanabilir.
Hata tamamen yutuluyor.
Retry yapılamıyor.
Teslimat gözlemlenemiyor.

Bunu güvenilir yapıya dönüştür.

Minimum güvenli yöntem:

try {
  await sendPushNotification(...);
} catch (error) {
  logger.error("Push notification failed", {
    eventId,
    eventType,
    recipientId,
    errorCode,
  });
}

Push başarısızlığı ana mesaj/talep işlemini kullanıcıya başarısız göstermemeli fakat backend çağrıyı gerçekten beklemeli ve hatayı kaydetmeli.

Daha sağlam tercih:

Ana DB işlemi
→ notification_event/outbox kaydı aynı transaction’da
→ worker pending eventleri gönderir
→ başarılıysa sent
→ geçici hatada retry
→ kalıcı hatada failed

Mevcut altyapıya uygun bir transactional outbox uygula.

Önerilen tablo:

notification_events
- id
- event_key UNIQUE
- event_type
- recipient_user_id
- entity_id
- payload JSONB
- status: pending | processing | sent | failed
- attempts
- next_attempt_at
- last_error_code
- created_at
- processed_at

Kurallar:

Aynı event iki kez bildirim oluşturmasın.
event_key deterministik/idempotent olsun.
Mesaj içeriği gibi gereksiz hassas veri payload’a yazılmasın.
Retry exponential backoff kullansın.
Maksimum deneme sayısı olsun.
Worker crash sonrası processing eventler kurtarılabilsin.
Secret/token loglanmasın.
Main API işlemi push hatası nedeniyle rollback edilmesin.
TOKEN SAHİPLİĞİ

Mevcut davranışı doğrula:

Token başka kullanıcıdaysa eski kayıt enabled=false
→ yeni kullanıcı için yeni kayıt

Eğer expo_push_token üzerinde global UNIQUE constraint varsa bu işlem yeni insert sırasında unique violation oluşturabilir.

Şemayı gerçekten kontrol et.

Güvenli sonuç:

Aynı fiziksel installation/token aynı anda yalnızca bir aktif kullanıcıya bağlı olmalı.
Logout sonrası eski bağlantı pasif olmalı.
Yeni login işlemi transaction içinde sahipliği güncellemeli.
Duplicate aktif kayıt oluşmamalı.
Unique constraint ile kod davranışı uyumlu olmalı.
Aynı kullanıcının farklı cihazları korunmalı.
Bir cihazdaki logout başka cihazın tokenını kapatmamalı.

Gerçek DB testi yap:

Token A → Kullanıcı 1
Kullanıcı 1 logout
Aynı cihazda Kullanıcı 2 login
Token A yalnızca Kullanıcı 2 için aktif
Unique constraint hatası yok
Kullanıcı 1’in başka cihaz tokenı aktif kalıyor
