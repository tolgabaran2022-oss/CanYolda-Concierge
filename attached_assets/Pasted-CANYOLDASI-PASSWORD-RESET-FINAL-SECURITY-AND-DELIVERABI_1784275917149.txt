CANYOLDASI — PASSWORD RESET FINAL SECURITY AND DELIVERABILITY FIXES

Current password reset flow:

- Express backend
- PostgreSQL
- Drizzle ORM
- Resend email delivery
- password_reset_tokens table
- raw token is SHA-256 hashed in database
- reset links expire after 30 minutes
- forgot-password mobile screen currently uses a 60-second resend cooldown
- sender:
  CanYoldaşı <noreply@canyoldasimapp.com>
- production reset URL:
  https://canyoldasimapp.com/reset-password

Implement the following three changes.

==================================================
1. PREVENT REUSING THE CURRENT PASSWORD
==================================================

When the user submits a new password through:

POST /api/auth/reset-password

the backend must verify that the new password is different from the user's current password.

Use the existing password hashing library and verification method.

Expected flow inside the same database transaction:

1. Hash the incoming reset token
2. Load the valid unused token
3. Load the corresponding user
4. Verify the token is not expired
5. Validate newPassword and confirmPassword match
6. Compare newPassword against the user's current password hash
7. If they match, reject the reset
8. If different, hash the new password
9. Update the user's password
10. Mark the reset token as used
11. Invalidate all other unused reset tokens
12. Revoke supported sessions
13. Commit

Do not compare password strings against stored hashes directly.

Use the existing secure comparison method such as:

bcrypt.compare()
argon2.verify()

or the project's actual password verification service.

User-facing Turkish message:

“Yeni şifreniz mevcut şifrenizden farklı olmalıdır.”

Return an appropriate safe client error, such as HTTP 400 or 422, according to the current API conventions.

Do not expose the current password hash.

Do not consume the reset token when this validation fails.

The user must be able to submit a different password using the same still-valid token.

==================================================
2. CHANGE RESEND COOLDOWN FROM 60 TO 120 SECONDS
==================================================

On the mobile:

“Şifremi Unuttum”

screen, change the resend cooldown from:

60 seconds

to:

120 seconds.

Expected behavior:

After a successful reset email request:

- disable the “Tekrar Gönder” button
- show a countdown starting from 02:00
- update every second
- enable the button when countdown reaches 00:00
- clean up the timer on unmount
- do not create multiple timers
- app background/foreground transitions must not reset the cooldown incorrectly

Prefer storing the cooldown end timestamp instead of decrementing an unreliable render counter.

Example:

resendAvailableAt = Date.now() + 120000

Calculate remaining time from that timestamp.

Format:

“Tekrar Gönder (01:59)”

The backend rate limit remains the real security authority.

Do not change the reset token expiry.

Reset token expiry must remain:

30 minutes

unless the existing backend is configured differently.

7. DMARC PRODUCTION DOCUMENTATION
==================================================

Do not modify DNS automatically.

Create exact manual instructions for adding DMARC at the domain provider.

Recommended initial record:

Type:
TXT

Host / Name:
_dmarc

Value:
v=DMARC1; p=none; rua=mailto:dmarc@canyoldasimapp.com;

However, first verify whether:

dmarc@canyoldasimapp.com

is a real mailbox capable of receiving reports.

If it does not exist, recommend creating a monitored mailbox or using a valid reporting address.

Do not configure p=quarantine or p=reject immediately.

Start with:

p=none

Then confirm SPF, DKIM and DMARC pass before gradually strengthening the policy.

Explain that domain verification in Resend already covers SPF and DKIM, while DMARC is an additional trust and anti-spoofing layer.
