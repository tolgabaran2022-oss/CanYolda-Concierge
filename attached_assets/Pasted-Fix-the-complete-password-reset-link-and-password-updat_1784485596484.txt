Fix the complete password reset link and password update flow in the CanYoldaşı application.

CURRENT ISSUE

1. The password reset email is delivered successfully.
2. The email contains a button linking to:

   https://canyoldasimapp.com/reset-password?token=...

3. Clicking “Şifremi Sıfırla” results in:

   ERR_CONNECTION_CLOSED
   “This site can’t be reached.”

4. The browser cannot open the reset-password page.
5. Therefore, the user cannot enter or save a new password.

IMPORTANT INITIAL FINDING

This is not currently a form-validation error.

The failure occurs before the reset page loads. Investigate the production domain, HTTPS configuration, deployment routing, and reset URL generation first.

TASK 1 — VERIFY THE PRODUCTION DOMAIN

Check the exact intended production domain.

The current email uses:

`canyoldasimapp.com`

Verify whether this is the correct domain or a typo.

Check:

- DNS records
- Domain verification
- SSL/TLS certificate
- HTTPS configuration
- Replit custom-domain configuration
- Whether the domain points to the active deployment
- Whether the deployment is currently running
- Whether port and proxy configuration are correct
- Whether both the root URL and reset route are reachable

Test these URLs directly:

- `https://canyoldasimapp.com`
- `https://canyoldasimapp.com/reset-password`

Report the real HTTP/network result of each request.

Do not claim that the token is invalid when the domain itself cannot establish a connection.

TASK 2 — FIX DEPLOYMENT AND HTTPS

Fix the cause of `ERR_CONNECTION_CLOSED`.

Verify:

- The custom domain is attached to the correct Replit deployment.
- The production deployment is active.
- DNS records match Replit’s current domain instructions.
- There are no outdated or conflicting A, AAAA, or CNAME records.
- The TLS certificate is valid and covers the exact hostname.
- HTTP correctly redirects to HTTPS.
- The application listens on the port provided by the hosting environment.
- The production server is not bound only to localhost.
- Reverse proxy and trusted-host settings accept the custom domain.
- No middleware, firewall rule, or host validation closes the connection.
- Environment variables are configured in the production deployment, not only in development.

Do not disable SSL verification as a workaround.

TASK 3 — MAKE THE RESET ROUTE DIRECTLY ACCESSIBLE

The following route must load when opened directly from an email:

`/reset-password`

If the application is a single-page application, configure the production server so direct navigation to `/reset-password` returns the application entry point instead of failing.

Check and fix:

- React Router or Expo Router route definition
- Replit deployment rewrite/fallback configuration
- Server-side route handling
- Static hosting rewrites
- Authentication middleware
- Route guards
- Redirect loops
- Case sensitivity
- Trailing-slash behavior

The reset page must not require an existing logged-in session.

TASK 4 — AUDIT THE RESET TOKEN ARCHITECTURE

Determine which password reset system is actually being used:

A. Supabase Auth recovery links, or  
B. A custom backend token stored in the application database.

Do not mix both systems accidentally.

The current email URL appears to use a custom query parameter:

`?token=...`

Trace and verify:

1. Where the token is generated
2. Whether only a secure hash is stored in the database
3. How the token is validated
4. Its expiration time
5. Whether it is single-use
6. Which user it belongs to
7. Whether it is invalidated after successful use
8. Whether requesting a new reset invalidates older tokens

Never log or expose the complete token in server logs or UI error messages.

If Supabase Auth is intended, use the official recovery flow consistently and correctly process the returned recovery session/code.

If the custom-token system is intended, keep the full flow server-side and update the user password securely through an authorized backend endpoint.

Never expose a Supabase service-role key to the frontend.

TASK 5 — FIX RESET URL GENERATION

Create the reset URL from one verified production environment variable, for example:

`APP_URL=https://canyoldasimapp.com`

Then safely generate:

`{APP_URL}/reset-password?token={URL_ENCODED_TOKEN}`

Requirements:

- No localhost URL in production
- No Replit development URL in production email
- No hardcoded outdated domain in multiple files
- No duplicate slash
- Correct HTTPS protocol
- Correct URL encoding
- Identical domain across email template, backend, authentication settings, and deployment

Fail clearly during configuration if `APP_URL` is missing. Do not silently send a broken reset URL.

TASK 6 — BUILD THE COMPLETE RESET PAGE

After the domain and route are accessible, `/reset-password` must:

1. Read the token safely.
2. Validate it through the backend.
3. Show a loading state during validation.
4. Show the password form only for a valid, unused, unexpired token.
5. Include:
   - “Yeni Şifre”
   - “Yeni Şifre Tekrar”
   - Show/hide password controls
   - “Şifremi Güncelle” button
6. Require matching passwords.
7. Enforce the application’s password policy.
8. Prevent repeated submissions.
9. Update the password securely.
10. Invalidate the token immediately after success.
11. Show a Turkish success message.
12. Redirect the user to the login page.

Suggested success message:

“Şifreniz başarıyla güncellendi. Yeni şifrenizle giriş yapabilirsiniz.”

TASK 7 — HANDLE INVALID LINKS SAFELY

Create clear Turkish states for:

Missing token:

“Şifre sıfırlama bağlantısı geçersiz.”

Expired token:

“Bu şifre sıfırlama bağlantısının süresi dolmuş.”

Already-used token:

“Bu şifre sıfırlama bağlantısı daha önce kullanılmış.”

Invalid token:

“Şifre sıfırlama bağlantısı geçersiz veya bozulmuş.”

Server error:

“Şifreniz güncellenemedi. Lütfen daha sonra tekrar deneyin.”

Include a visible action:

“Yeni Şifre Sıfırlama Bağlantısı İste”

Do not reveal whether an email address or account exists.

TASK 8 — SECURITY REQUIREMENTS

- Store only a cryptographic hash of a custom reset token.
- Use a cryptographically secure random token.
- Apply a short expiration period.
- Enforce single use.
- Invalidate previous tokens when a new request is created.
- Rate-limit password reset requests and token validation attempts.
- Do not include passwords or complete tokens in logs.
- Do not expose service-role or administrative credentials to the client.
- Invalidate relevant sessions after the password changes where supported.
- Prevent token reuse and replay attacks.
- Do not send the token to third-party analytics.
- Use `Referrer-Policy: no-referrer` on the reset page where appropriate.
- Replace the URL containing the token in browser history after successful validation where safely possible.
