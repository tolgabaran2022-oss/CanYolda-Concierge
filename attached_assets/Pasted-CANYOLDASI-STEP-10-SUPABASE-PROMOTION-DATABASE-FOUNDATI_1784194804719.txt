10. ROW LEVEL SECURITY
==================================================

Enable RLS on the promotion purchase table.

Normal authenticated clients must NOT be able to:

- insert verified purchases
- set purchase_status = verified
- set purchase_status = processed
- set arbitrary duration_days
- set arbitrary transaction_identifier
- set arbitrary promotion_expires_at
- modify another user's purchase record

The secure backend / Edge Function will perform verified writes.

Recommended policy behavior:

Authenticated users may read only their own promotion purchase history if the application needs it.

Public users must not read sensitive transaction records.

Client-side insert/update/delete should be blocked unless the current architecture has a narrowly scoped safe pending-intent flow.

Do not expose:

transaction identifiers
purchase tokens
private verification payloads

through public selects.

11. PROTECT PROMOTED_UNTIL
==================================================

Audit existing RLS policies on the listing table.

Critical requirement:

A normal authenticated user must not be able to directly run:

supabase
  .from(listingTable)
  .update({
    promoted_until: "2099-01-01"
  })

and successfully promote their listing.

Implement a safe architecture that protects promotion-managed fields without breaking ordinary listing edits.

Possible approaches:

- revoke direct update access to promotion fields through a secure RPC architecture
- separate promotion state into a server-managed table
- use a trigger or column-level privilege strategy supported by the current architecture
- route listing updates through safe database functions

Choose the solution that actually works with Supabase/Postgres and the existing app.

Do not claim RLS can inspect omitted versus unchanged columns without implementing it correctly.
